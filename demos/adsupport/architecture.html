Dual-control support eval: the components

A standalone customer and a standalone simulated app surround the real thing under test: an Andyur conversational agent. Both the agent and the customer act on one shared world, and a ticket only closes if they coordinate.

2What is in each component

Orchestrator + scorer

run_andyur.py
Runs one episode and scores it. Defines no agent, policy, or tools.
  • provisions the SUT, triggers a conversation
  • turn loop: send /turn, drain /events, let the customer act
  • stall guard (snapshot-diff) + scoring from /goal
  • --transcript prints the full session

Customer simulator

agent.py · scenarios.py
A τ²-style user: an LLM in-character with its own tools on the app.
  • persona + hidden goal, temperature 0.8
  • advertiser tools only (update payment, edit creative, resubmit, resume)
  • drives the chat and actually acts on the app service

Scenarios

scenarios.py
The test cases. Each seeds a broken world and defines success.
  • persona, hidden goal, seed (build the app state)
  • goal predicate over the final app state
  • a unit test proves each is unsolvable by one party alone

SUT definition + provisioning

agent/instructions.md · provision.py
Who the agent IS, authored separately from the harness.
  • instructions.md: the standing policy (a file, not code)
  • provision.py: creates the agent, writes its mind, generates mcp.json
  • identity (policy, tools) vs deployment (paths, url) kept apart

Andyur conversation (the SUT)

Andyur
A real persistent Andyur conversational agent. The thing being tested.
  • grounded on its instructions.md policy
  • one live session across all turns
  • calls its MCP tools to act; streams replies as events

Support MCP toolserver

mcp_support.py
The agent's tools, loaded via the agent's mcp.json.
  • FastMCP server: 4 reads + 5 admin actions
  • agent surface only, no advertiser tool
  • each tool calls the app as actor=agent

Andyur control plane

server + daemon
Runs the agent; the harness talks to it over HTTP.
  • /trigger a conversation, /turn in, /events out
  • daemon launches the session; runner loads the agent's mcp.json

The simulated app (shared world)

app.py · app_server.py
One authoritative state both sides mutate. Source of truth for success.
  • AdsPlatform: accounts, campaigns, ads, charges + rules
  • dispatch(): enforces the actor's authority
  • HTTP: /seed /call /snapshot /goal

3One turn, end to end

How a single exchange flows through the components. The dual control is steps 3 and 5.

  1. Customer sim produces a message in-character, from persona + goal
  2. Harness sends it as a turn POST /runs/<id>/turn → Andyur
  3. The Andyur agent diagnoses and acts mcp__adsupport__* → MCP server → app (actor=agent)
  4. Agent's reply streams back GET /events → harness drains chunks
  5. Customer sim reacts and acts its advertiser tools on the app (actor=advertiser)
  6. Harness scores GET /goal; resolved? else loop

4Why it is split this way

The SUT is a real Andyur agent, not a mock. You test the thing you ship, not a stand-in. The app and the customer are the harness around it.

The world is a service, not an in-process object. Two separate processes (the Andyur agent and the customer sim) must share one authoritative state, so the world has to be a service both reach. It is also the faithful τ²-bench shape.

The agent's identity is authored, not coded. An Andyur agent is a mind (instructions.md) plus a tool manifest (mcp.json). The harness provisions and drives it; it never defines it.

The authority boundary is enforced twice. The agent has no advertiser tool to call (its tool surface), and the app refuses any cross-surface call anyway (dispatch). The policy guides; the boundary holds regardless.
